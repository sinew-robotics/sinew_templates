# Demo media assets

Every file directly in this directory (not under `reference/`) was
synthesized locally by `template/scripts/generate_demo_media.py` in this
repository. Nothing at this level was downloaded, photographed, recorded, or
copied in from a third party. All random sources in the generator are seeded
through local `random.Random(seed)` instances (never the shared global
`random` state), so running the script reproduces byte-identical files.

The `reference/` subdirectory is the one deliberate exception to all of the
above: it holds one third-party Meta AI figure, copied in on purpose as a
worked example, plus one derivative of it produced by
`make_transparent.py`. See "Reference: third-party V-JEPA 2 figures" below
-- it is a separate provenance story from everything else in this file, and
is called out by directory location specifically so the two are never
confused at a glance.

Frame synthesis uses Pillow only (plus the stdlib `random` and `math`
modules) -- no numpy, no matplotlib -- matching the dependency discipline
of the sibling `template/scripts/make_transparent.py` tool. ffmpeg/ffprobe
are used only to encode, mux, and extract video, never to synthesize
image content.

These files exist to give the v1.2.0 gallery slides real, renderable media
to demonstrate the deck's raster/vector and video-handling conventions
(background stripping, native aspect ratio, poster-frame selection). They
are illustrative demo assets, not evidence figures, and carry no scientific
claims.

License status: same as the rest of this repository (see the repository's
top-level license). Being demo/placeholder content does not exempt these
files from that license; they are original, locally generated work product.

Regenerate everything with `python3 template/scripts/generate_demo_media.py`,
or a single asset with `--only <name>` (`diagram`, `diagram-transparent`,
`photo`, `video`, `poster`, or `gif`, repeatable) to avoid disturbing files
you did not mean to touch -- see "The --only flag" below for why this
exists. The bare, argument-less form above regenerates exactly those six
files and nothing under `reference/`: `reference-transparent` is a seventh,
opt-in-only `--only` choice, deliberately excluded from the default run --
see "Reference: third-party V-JEPA 2 figures" below for why.

## demo-diagram.png and demo-diagram-transparent.png are a pair -- do not "fix" the input

`demo-diagram.png` is deliberately drawn on a flat WHITE background: it is
the tool's INPUT, meant to be shown next to `demo-diagram-transparent.png`
as a before-and-after pair demonstrating what
`template/scripts/make_transparent.py` does. If a future editor is tempted
to strip or recolor `demo-diagram.png`'s background because it looks wrong
sitting on a dark slide, that removes the whole point of the pairing --
leave it white.

Both files use black ink for every stroke and label. Composited onto a
dark profile background (see the origami check below), the black ink and
the dark surface are close in luminance, so the transparent diagram is low
contrast/hard to read on origami, blueprint, and movement specifically --
this is an inherent property of drawing in black ink, not a defect in the
transparency step (which is proven clean below: no white halo, no fringe,
no residual brightness in the background region). If the gallery slide
needs the diagram to read well on a dark profile, that is a content choice
for the slide (e.g. picking a profile where it is shown, or redrawing the
source in a lighter ink) -- it is not something `make_transparent.py` can
or should compensate for.

### demo-diagram-transparent.png

- What: `demo-diagram.png` with its white background stripped to alpha,

- Exact command:

  ```
  python3 template/scripts/make_transparent.py \
    template/assets/media/demo-diagram.png \
    -o template/assets/media/demo-diagram-transparent.png \
    --tolerance 12.0 --force
  ```

  (equivalently: `python3 template/scripts/generate_demo_media.py --only diagram-transparent`,
  which requires `demo-diagram.png` to already exist)
- Resolution: 1200x480 (unchanged). Format: PNG, RGBA.
- Size: 12882 bytes.
- SHA-256: `873e3bd00d7cf502e3a3b84d48eb7147a96814cbac24a91b55a3f3e54d1fd30c`

This is the SECOND (final) regeneration against `make_transparent.py`. The
tool changed twice during v1.2.0 development; both times the previous
result here turned out to be stale and was redone against the newer tool,
each time re-measured from scratch rather than assumed carried-over. The
gate the final tool uses is a saturation RATIO (`spread / max(d, 1)`, with
`RATIO_LOW=0.85`, `RATIO_HIGH=0.99`, `FEATHER_WIDE=160`,
`FEATHER_NARROW=16`), not raw channel spread, and decontamination now
derives its coverage estimate from `d` (distance from white) directly
instead of from the display alpha -- both changes affect any partially
transparent pixel's recovered color, including neutral black ink like
this diagram's, which is why a black-line-art asset still needed
re-verifying even though the headline fix was about hue.

#### Tolerance: how 12 was chosen (re-derived against the final tool)

`demo-diagram.png` contains real antialiased pixels in the risk band
(mostly font-rasterization edges on the title text): a corner-to-corner
scan of the source PNG found 632 near-white-but-not-pure pixels (every
other row/column sampled), with distance-from-white spanning 4 to 152.

Tolerance was swept over {5, 8, 10, 12, 15, 18, 20} against the FINAL tool
(checksum confirmed unchanged immediately before and after the sweep) and
each result graded on three counts derived directly from
`demo-diagram.png`'s own pixels:

- `pale & opaque`: alpha == 255 with SOURCE `min(r,g,b) >= 200` -- the
  originally reported bug (pale pixel stuck opaque, undecontaminated).
- `midgray & opaque`: alpha == 255 with SOURCE `90 <= min(r,g,b) < 200` --
  the previously documented, tolerance-sensitive residual.
- `nonzero_decon_px` / `max_decon_channel`: among every partially
  transparent pixel (`0 < alpha < 255`), how many decontaminate to
  anything other than pure `(0, 0, 0)`, and the largest channel value
  among them. For pure black ink the mathematically correct recovered
  color is exactly black at every point along the blend, so any nonzero
  value here is a decontamination defect, not a matter of degree.

| tolerance | pale & opaque | midgray & opaque | nonzero decon px | max decon channel | output size |
|----------:|--------------:|------------------:|------------------:|-------------------:|------------:|
| 5         | 0             | 0                  | 0                  | 0                   | 13032 bytes |
| 8         | 0             | 0                  | 0                  | 0                   | 13056 bytes |
| 10        | 0             | 0                  | 0                  | 0                   | 13029 bytes |
| **12**    | **0**         | **0**              | **0**              | **0**               | 12882 bytes |
| 15        | 0             | 0                  | 0                  | 0                   | 12915 bytes |
| 18        | 0             | 0                  | 0                  | 0                   | 12803 bytes |
| 20        | 0             | 0                  | 0                  | 0                   | 12869 bytes |

All three counts are zero at every tolerance tested, 5 through 20 -- a
stronger result than the previous tool revision (which still showed 144px
and 33px of `midgray & opaque` at tolerance 5 and 8 respectively). This
follows directly from the ratio formula: for neutral ink, `spread` is
always 0 (r == g == b everywhere on the blend line), so `ratio = 0` for
every antialiased pixel regardless of distance from white, which always
selects `FEATHER_WIDE` (160, wider than the previous revision's 140) --
black/neutral line art is exactly the case this tool now fully handles
(per the tool author's own docs; the remaining residual is for
near-maximally-saturated colored ink, which does not apply here).

Since every tested tolerance is equally clean, 12 was kept: it sits at the
tool's own `--tolerance` default and centrally in the documented
"clean vector/PNG line art, including antialiased edges: 5-15" band, with
no evidence favoring any other value in range for this asset.

#### Proof: dark and light composite luminance

An alpha histogram is exactly what let the original bug through (it hides
a pixel that is opaque-but-pale), so the proof here is a real composite
onto both a dark and a light Sinew surface, not a histogram. Re-measured
against the exact shipped tolerance-12 file (sweep output and
`generate_demo_media.py`'s output are byte-identical, confirmed by
checksum).

"Region that should be transparent" is defined as every source pixel that
is exactly `(255, 255, 255)` (138998 of them, sampled every other
row/column) -- unambiguous flat background, ground truth from the PNG
itself, not inferred.

- Origami dark surface `#131416` (relative luminance 0.00697, i.e.
  19.94/255): composited the tolerance-12 RGBA result over this color and
  measured the MAX luminance inside the should-be-transparent region.
  **Result: 0.00697 (19.94/255) -- identical to the bare background
  color, to full floating-point precision.** No brightening, no residual
  white haze anywhere in the flat background.
- Paper light surface `#fbfaf5` (relative luminance 0.95473, i.e.
  249.86/255): composited the same result over this color and measured
  the MIN luminance inside the same region (the direction a translucent
  gray haze -- invisible against dark, visible as a smudge against a pale
  surface -- would show up). **Result: 0.95473 (249.86/255) -- identical
  to the bare background color.** No darkening, no smudge.
- `make_transparent.py`'s checksum was confirmed unchanged across both the
  sweep and this final measurement.

Both checks passing simultaneously is the actual proof: a fix that only
zeroed brightening on dark, or only zeroed darkening on light, would still
leave a decontamination artifact that "hides on one surface, shows on the
other" -- exactly the failure mode being guarded against, since all nine
style columns display this asset and they are not all dark
(`--sinew-bg`: origami `#131416`, blueprint `#081c33` are dark; paper
`#fbfaf5`, high-contrast `#ffffff`, scholar `#f7f3ff`, the-give `#e9eef5`,
the-meeting `#ecf3f2`, unmasked `#f7f9fb`, movement `#f6f8fb` are light).
Visual spot-check: the composited PNG was inspected directly over both
`#131416` and `#fbfaf5` -- clean edges, no fringe, no halo, no smudge on
either.

#### Known limitation that does NOT apply here

The tool's remaining documented residual is for near-maximally-saturated
colored ink (e.g. pure blue `(0, 0, 255)`): at the single-pixel level, a
21.6%-covered pure-blue antialiasing pixel and deliberately authored pale
yellow can share the exact same `(d, spread)` pair, so no per-pixel test
can separate "fading edge" from "intentional pale content" for saturated
hues -- this is proven unfixable in a per-pixel model, not a bug. It does
not affect `demo-diagram.png`: black ink has `spread = 0` everywhere,
which the ratio formula always resolves to the wide, forgiving feather.
Future vivid-color line art added to this repository should use the
`.plate` theme class instead of `make_transparent.py`.

### vjepa2-abstract-transparent.png -- the make_transparent.py worked example, on a much harder input

`demo-diagram.png`/`demo-diagram-transparent.png` earlier in this file is
the easy case for `make_transparent.py`: pure black neutral ink, `spread =
0` everywhere, always resolves to the tool's forgiving wide feather. This
asset is the intentionally hard case, run against the exact same, FINAL
`make_transparent.py` used for that pair -- and the honest result is a
genuine, disclosed limitation, not a clean win.

`vjepa2-abstract-new.png` mixes three very different pixel populations:

1. Antialiased black text and thin slate-blue (`(70, 89, 104)`) connector
   lines -- the well-handled case, same as the diagram pair above.
2. Flat GREY box fills (`(222, 227, 233)`, used for the `predictor`,
   `encoder`, and `ema encoder` shapes) -- CONTENT, not background, and it
   must stay opaque.
3. A saturated RED alert box (`L1`, plus the `z` mask-token circle and
   `stop-grad` mark) with a pale pink fill (`(255, 229, 229)`) -- the
   documented near-maximally-saturated-ink case, where a partially-covered
   red edge pixel and deliberately authored pale pink content can be
   mathematically identical to the tool.

#### Tolerance: re-derived from scratch, not reused from the diagram pair

Swept independently against this asset (checksum of `make_transparent.py`
confirmed unchanged across the sweep: `fb0ce244998967b8ad98525ef7e76cb7`).
For each tolerance, every exact-color source pixel of the grey fill (15446
px) and the pink fill (1629 px) was tracked to its output alpha (uniform
within each color -- min, mean, and max coincide), together with the
background-cleanliness proof (see next section) over every exact `(255,
255, 255)` source pixel (93015 px):

| tolerance | grey-fill alpha (/255) | pink-fill alpha (/255) | red-core alpha | max lum, origami | min lum, paper |
|----------:|------------------------:|-------------------------:|----------------:|------------------:|----------------:|
| 3         | 40                       | 255                       | 255              | 19.9318            | 249.8516         |
| **5**     | **32**                   | **211**                   | **255**          | **19.9318**        | **249.8516**     |
| 8         | 20                       | 89                        | 255              | 19.9318            | 249.8516         |
| 10        | 12                       | 8                         | 255              | 19.9318            | 249.8516         |
| 12        | 4                        | 0                         | 255              | 19.9318            | 249.8516         |
| 15        | 0                        | 0                         | 255              | 19.9318            | 249.8516         |
| 18-25     | 0                        | 0                         | 255              | 19.9318            | 249.8516         |

("red-core" = every source pixel with `r >= 250, g <= 10, b <= 10`, i.e.
the box's solid red ink away from any edge; 598 px.)

**The background half of this is unconditionally clean at every tolerance
tested, 3 through 25**: max luminance in the should-be-transparent region
composited over origami `#131416` is 19.9318 at every single tolerance --
identical to the bare surface's own luminance (0.2126x19 + 0.7152x20 +
0.0722x22 = 19.9318) to full floating-point precision, no brightening
whatsoever. Composited over paper `#fbfaf5`, min luminance in the same
region is 249.8516 at every tolerance -- identical to the bare surface
(0.2126x251 + 0.7152x250 + 0.0722x245 = 249.8516), no darkening. Both
proofs use the same method as the diagram pair above: the ground-truth
region is every source pixel that is exactly `(255, 255, 255)`, not a
cropped rectangle (an earlier draft of this sweep mistakenly sampled a
rectangular top margin that included the antialiased "V-JEPA 2" title text
and produced a spurious max-luminance reading of 38 on origami; switching
to the exact-white-pixel method used elsewhere in this file corrected it).

**The content half is where this asset genuinely fails, and no tolerance
fixes it:**

- **Grey fill never reaches usable opacity, at any tolerance, including
  below the documented floor.** `(222, 227, 233)` has `d = 33` (distance
  from white) and `spread = 11`, `ratio = 0.33` -- comfortably under
  `RATIO_LOW = 0.85`, so it always gets the tool's WIDE feather (160),
  which is the branch meant for antialiased neutral ink, not a flat
  content fill. Because feather width does not depend on tolerance, and
  `d = 33` is far smaller than the 160-wide ramp, this pixel is
  mathematically incapable of reaching alpha 255 at ANY tolerance: even at
  tolerance 0 (`cutoff = 0`), the ceiling is `round(33 * 255 / 160) = 53`
  out of 255 (21%) -- and every tolerance in the documented "clean
  vector/PNG line art" band (5-15) does substantially worse (32 at 5, down
  to 0 -- fully erased -- at 15). This is a structural property of this
  color relative to the ratio-gated feather formula, not a tuning miss:
  **there is no tolerance value, in or out of the documented range, at
  which this grey fill survives as visually solid content.**
- **Pink fill only reaches full opacity below the documented tolerance
  floor.** `(255, 229, 229)` has `d = 26`, `spread = 26`, `ratio = 1.00` --
  at or past `RATIO_HIGH = 0.99`, so it always gets the NARROW feather
  (16), which is exactly the tool's documented near-maximally-saturated-ink
  ambiguity (this pale pink and a 21.6%-covered pure-blue edge pixel would
  be indistinguishable to the same test at matching `d`/`spread`). Alpha
  255 requires `cutoff <= d - 16 = 10`, i.e. tolerance `<= 3.92` -- below
  the tool's documented 5-15 floor for clean line art. Within the
  documented range, the best available (tolerance 5) is 211/255 (83%,
  visibly present but translucent, not solid); by tolerance 12 it is fully
  erased (0).
- **Both partially-transparent fills were also MISCOLORED, not just faded,
  by decontamination -- a second, compounding defect on top of the opacity
  loss above. This half is now FIXED by a spatial gate; see "Decontamination
  spatial gate fix" below for the mechanism and full before/after numbers.**
  Decontamination (see the module docstring, "Color decontamination")
  recovers each partial-alpha pixel's color under the assumption that it is
  a genuine antialiased blend of white and some fully-saturated ink --
  correct for a fading edge, but was, before the fix, applied uniformly to
  every partially-transparent pixel regardless of position, which is wrong
  for a deliberately pale, less-saturated FILL: a fill pixel deep inside a
  shape was never actually composited against the white background (only
  pixels near the background could have been), so it is not fading toward
  anything and decontaminating it recovers a meaningless color. Before the
  fix, measured on the tolerance-5.0 file: the pink fill's output pixel was
  `(255, 0, 0, 211)` -- decontamination recovered PURE RED, the same color
  as the box's own border, not the pale pink the source actually specifies.
  Composited at 83% coverage this read as a nearly-solid red box with no
  visible distinction between border and fill, a real loss of the original
  design's two-tone structure, not merely "the same box, fainter." The grey
  fill's output pixel was `(0, 39, 85, 32)` -- decontamination recovered a
  dark navy-black, not the light blue-grey the source specifies, on the
  (structurally correct, per the docstring's own black-ink assumption) but
  here-wrong premise that any partially-transparent pixel must be fading
  toward black. At 32/255 coverage this was nearly invisible either way, so
  the miscoloring was moot for the grey fill in practice, but it compounded
  the pink fill's defect into something worse than fading alone.
- The solid red ink itself (the box border's core color, away from any
  edge) stays fully opaque (alpha 255) at every tolerance tested -- its
  distance from white is far too large to be affected either way.

**Conclusion: no tolerance both clears the white background and preserves
the grey fills as opaque content** -- confirmed by direct sweep, not
assumed. This matches (and is independent evidence for) the guidance in
`template/docs/figures-and-tables.md`, "White backgrounds": use a plate,
not `make_transparent.py`, when "white in the source has meaning (a filled
box, a callout, content you must not alter)". This asset is exactly that
case; it was still run through the stripping tool, on purpose, because the
point here is to demonstrate the tool's real, disclosed limits rather than
cherry-pick a color scheme that flatters it.

Tolerance **5.0** was kept as the least-bad tradeoff: it is the tool's own
documented floor for clean line art (not reused from the diagram pair's
12.0), the background proof holds at full precision, the red ink's solid
core is untouched, and the pink fill gets its best in-range result (83%
opacity) even though that is short of fully solid. The grey fill is NOT
rescued by this choice -- disclosed above, not hidden. This section is
about OPACITY; the separate COLOR defect on both fills is covered next, and
is now fixed for the pink fill (and improved for the grey fill).

#### Decontamination spatial gate fix

The miscoloring defect above (pink fill decontaminated to solid red, grey
fill to dark navy) is fixed by gating decontamination spatially, in
`decontaminate()`/`build_near_background_mask()`: only a partially-
transparent pixel within `DECONTAMINATION_RADIUS` (3, 8-connected/chebyshev)
of an actual fully-transparent (`alpha == 0`) pixel is un-premultiplied
against white. A pixel farther than that from any fully-transparent pixel
was never composited against the background, so its color is left exactly
as the source specifies; only its alpha still comes from the existing
tolerance/feather ramp (unchanged by this fix).

**Why radius 3, measured rather than guessed** (8-connected BFS distance
from the nearest `alpha == 0` pixel, on the shipped tolerance-5.0 alpha
map, before this fix):

| population | n | min dist | max dist | distribution |
|---|---:|---:|---:|---|
| pink fill, `(255,229,229)` | 1629 | 1 | 16 | 4 px at dist 1; then a hard gap (**zero** px at dist 2 or 3); 91 px at dist 4; rising to dist 16 |
| grey fill, `(222,227,233)` | 15446 | 1 | 34 | 442/914/888 px at dist 1/2/3 (14.5% of the fill); remaining 85.5% spread from dist 4 to 34 |
| documented curved z-circle pixel, `(245,148,149)` | 1 | 1 | 1 | -- |
| all other genuine red-hued antialiasing pixels on the L1/z-circle box (partial alpha, not the exact pink-fill color) | 60 | 1 | 12 | 25/6/9 px at dist 1/2/3 (67%); 11 px at dist 4 (unrelated photo-thumbnail antialiasing near y=286-329, not this box); 9 outlier px at dist 4-12 (2 of those are pale internal red/pink-fill-to-border antialiasing near y=72-73, also not background-adjacent) |

The pink fill's distribution has a hard cliff (nothing at distance 2 or 3
at all) that radius 3 sits cleanly inside: it catches essentially the
entire genuine-antialiasing population (all of the z-circle boundary, and
the bulk of the other 60 red-hued edge pixels) while sparing 1625 of 1629
(99.75%) pink-fill pixels. It cannot do better than that 99.75%: the 4
stray pink pixels at distance 1 are genuinely, physically adjacent to a
transparent pixel (a 1px leak point in the border, most likely where the
"L1" text glyph or a border corner thins to nothing), indistinguishable at
the pixel level from real antialiasing at that same distance -- this is the
same fundamental single-pixel-neighborhood limit the module docstring's
"Known residual limitations" section already describes for color, now
also true spatially at the minimum possible radius. Widening the radius
would not rescue these 4 pixels (they are already caught at radius 1) and
would only pull in more of the pink fill's dist-4-and-up bulk; narrowing to
radius 1 or 2 would still catch the 4 stray pixels (unavoidable) while
missing part of the z-circle's dist-3 antialiasing. Radius 3 is the point
that covers the documented genuine-antialiasing population without giving
up any more of the fill than the unavoidable 4 pixels.

The grey fill's fix is partial by the same measurement: because these
boxes have no opaque border walling off their fill from the background
(see "--keep-largest-region" below), a much larger fraction (14.5%, 2244
of 15446 px) sits within radius 3 of the background and is still
decontaminated (still miscolored, unchanged from before this fix). The
remaining 85.5% (13202 px) now keeps its true source color. This does
NOT touch the grey fill's separate, structural ALPHA-ceiling defect
(documented above: 53/255 is the mathematical ceiling at any tolerance) --
that defect is about the alpha ramp's feather width, not about
decontamination, and this fix only changes which pixels get
recolored, never their alpha. **The grey fill's alpha ceiling remains
completely unfixed and undisclosed-nowhere-but-here would be wrong: it is
still exactly the defect described above.**

**Measured before/after, tolerance 5.0** (interior pink-fill pixel
`(278, 77)`; nearby border pixel `(242, 77)`, same row):

| pixel | source | alpha | before this fix | after this fix |
|---|---|---:|---|---|
| pink fill `(278, 77)` | `(255, 229, 229)` | 211 | `(255, 0, 0, 211)` | `(255, 229, 229, 211)` |
| border `(242, 77)` | `(255, 0, 0)` | 255 | `(255, 0, 0, 255)` | `(255, 0, 0, 255)` (unaffected -- alpha 255 always skips decontamination) |

The border-versus-fill distinction is restored: the fill is now
numerically pale pink at 83% opacity, distinct from the border's solid
red, rather than both reading as the same red.

Across the whole pink fill: 1625/1629 px now output `(255, 229, 229, 211)`
(correct color, unchanged opacity); the 4 stray dist-1 px still output
`(255, 0, 0, 211)` (unavoidable, see above). Across the whole grey fill:
13202/15446 px now output `(222, 227, 233, 32)` (correct color, unchanged
32/255 opacity); the 2244 dist-1..3 px still output `(0, 39, 85, 32)`
(unchanged from before this fix).

**Everything else this fix must not break, verified:**

- Background cleanliness is untouched (this fix only gates color, never
  alpha): max luminance in the should-be-transparent region composited
  over origami is still 19.9318 (identical to bare-surface luminance to
  full precision); min luminance composited over paper is still 249.8516.
  Same method as above, same result, re-measured after this fix.
- Corner and mid-edge pixels `(0, 0)`, `(331, 0)`, `(0, 392)`, `(331, 392)`,
  `(166, 0)` are still all `(255, 255, 255, 0)`.
- No new white halo on either documented edge case: the straight box edges
  (e.g. `(254, 14, 14)`, `(254, 33, 33)`) are still fully opaque
  (`alpha == 255`) and therefore still skip decontamination entirely, same
  as before this fix. The curved z-circle boundary's documented pixel is
  still decontaminated the same way as before this fix -- source `(245,
  148, 149)` still recovers to `(231, 0, 2)` at alpha 236 -- because that
  pixel sits at distance 1 from the background, well inside the radius-3
  gate; see "Fringe" below, which is unchanged by this fix (that residual
  is not what this fix targets).
- Determinism: regenerated twice in a row into separate scratch
  directories; both runs, and the file actually shipped in this
  repository, produced the identical SHA-256 below. Source file confirmed
  byte-for-byte unchanged (`cmp`) after every run.
- `python3 template/scripts/validate.py` passes.

#### --keep-largest-region was tested and rejected for this asset

Because the pink fill is a small, real casualty, `--keep-largest-region`
was tried as a possible fix (it protects background-colored pixels
enclosed by opaque artwork from being stripped). Result, at tolerance 5:

- The `L1` box's pink fill IS enclosed (its interior is walled off from the
  image border by the fully-opaque red border), so `--keep-largest-region`
  does rescue most of it -- but not uniformly (worst-case pixel in the
  fill, near the border/text boundary, still only reaches 211/255; only
  pixels strictly interior reach 255).
- The grey fills are NOT enclosed -- the `predictor`/`encoder`/`ema
  encoder` shapes have no separating border between their fill and the
  white background, so the flood fill used by `--keep-largest-region`
  flows straight through them from the image border, exactly as if the
  flag were off. Alpha stayed at 32/255, unchanged.
- New, worse defect: this diagram is full of text with closed counters
  (`predictor`, `encoder`, `camera`, `robot arm`, `mask`, `ema`, ...).
  `--keep-largest-region` treats every non-fully-opaque pixel as a
  flood-fill "candidate," including the antialiased interior of every
  closed letterform (the inside of a lowercase `e`, `a`, `o`, `d`, `R`,
  `P`, ...) -- each one is enclosed by its own letter strokes and gets
  forced back to fully opaque WHITE. Measured: max luminance in the
  should-be-transparent region composited over origami jumped from
  19.9318 (clean, plain mode) to **255.0** -- solid white letter-interior
  blotches scattered across the entire dark-surface composite. This is
  worse than the fill-opacity problem it was meant to fix, since it
  affects far more of the image and is visually louder (pure white on a
  near-black surface) than a translucent grey box. **Plain mode (no
  `--keep-largest-region`) was kept for the shipped file** for this
  reason.

#### Fringe: the red box's residual, measured and disclosed rather than hidden

The box's straight edges are clean: every red-to-white transition on the
`L1` box's four sides is a single antialiased pixel with `d >= 209` (e.g.
`(254, 14, 14)`, `(254, 33, 33)`), which the narrow-feather branch resolves
to fully opaque at every tolerance tested from 3 to 25 -- no visible fringe
on the straight edges at the shipped tolerance.

The disclosed residual is smaller and lives on curved geometry -- the `z`
mask-token circle's antialiased boundary is not a hard single-pixel step
the way the box's straight edges are. At tolerance 5.0, one representative
measured pixel: source `(245, 148, 149)`, decontaminated to `(231, 0, 2)`,
alpha 236. Composited over origami: luminance 46.64 (bare surface 19.93,
delta +26.7 -- a faint red-tinted lift, visible on close inspection).
Composited over paper: luminance 64.36 (bare surface 249.85, delta -185.5
-- a clearly visible dusky-red smudge against the light surface). This is
exactly the tool's documented residual for near-maximally-saturated ink
(module docstring, "Known residual limitations," #1): a curved edge's
antialiasing pixel and deliberately authored pale-red content can share
the same `(d, spread)` pair, so no per-pixel test separates them, and the
tool's own tested tradeoff keeps content preservation over halo
elimination for this color family. This fringe is disclosed here rather
than cropped out of the measurement.

## The --only flag

`generate_demo_media.py` originally had no way to regenerate a single
asset: any full run touched all six files. That caused a real problem
during v1.2.0 development -- testing an unrelated numpy-removal fix
required a full run, which silently regenerated
`demo-diagram-transparent.png` against whatever revision of
`make_transparent.py` happened to be on disk at that moment (another
agent was mid-rework on it), leaving that one file's provenance uncertain
for a period and forcing a redo. `--only <name>` (repeatable; choices
`diagram`, `diagram-transparent`, `photo`, `video`, `poster`, `gif`) was
added to `main()` so any single asset can be regenerated without touching
the other five -- e.g. `--only diagram-transparent` was used for every
run in the "Tolerance" and "Proof" sections above, and confirmed (by
checksum) not to change `demo-diagram.png`, `demo-photo.jpg`,
`demo-clip.mp4`, `demo-clip-poster.jpg`, or `demo-loop.gif`. It enforces
its own dependencies: `--only diagram-transparent` errors clearly if
`demo-diagram.png` does not already exist (and `diagram` was not also
selected in the same run), and `--only poster` the same way for
`demo-clip.mp4`/`video`.

A seventh choice, `reference-transparent`, was added later for
`vjepa2-abstract-transparent.png` (see "Reference: third-party V-JEPA 2
figures" above). It is intentionally NOT one of the six files a bare,
argument-less run regenerates -- its source is a third-party input this
script must never create, so it is opt-in only, and it enforces its
dependency the same way the two pairs above do, except that the missing
dependency here can never be auto-generated by this script: `--only
reference-transparent` fails immediately and clearly if
`reference/vjepa2-abstract-new.png` is not already on disk.
